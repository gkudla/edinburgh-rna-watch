STEP 6 — REPORT.
Nobody reads this session's transcript, so the report must leave the session: create
a GitHub issue on the main branch, and send the summary via the notification channel
(PushNotification), which reaches gkudla@gmail.com. If a mail tool is available, email
it too; do not treat a missing mail tool as a failed run.

`gh issue create` and `gh label list/create` go through GitHub's GraphQL endpoint,
which is BLOCKED in this environment (HTTP 403). Use the REST API instead. Write the
body to a temporary file, build the JSON payload from it with python3 (do not
hand-quote it), and post:

  gh api repos/gkudla/edinburgh-rna-watch/issues --method POST --input <payload.json>

with payload {"title": ..., "body": ..., "labels": [...]}. Labels jobs, matches and
quiet already exist; list labels with
`gh api repos/gkudla/edinburgh-rna-watch/labels --jq '.[].name'` if you need to check.

Title: "Edinburgh RNA jobs — YYYY-MM-DD" using today's date.

KEEP THE BODY SHORT. It contains only the matches and the coverage line. Aleksandra
may forward it to someone with no access to this repo or session, so no references to
"the state file", "last run", or anything else only visible from inside the routine.

Do NOT include, in any form: postings you opened and ruled out; any explanation of why
an irrelevant job is irrelevant; expired or closed postings you found; a recap of jobs
reported on earlier runs; a list of which sources were verified. That is work you did,
not information she needs. If a posting is not a reportable match, it does not appear
in the report at all.

If there are new matches, the body is:

  N new match(es) today.

  Then for each match, as a markdown block:
  ### <job title>
  - Employer and department: ...
  - Location: ...
  - Salary: ... (omit the line if unknown)
  - Closing date: ...
  - Link: <full URL>
  - Why it matches: <one line on the research area>

  Order strongest RNA and molecular-biology matches first. Put any marginal
  inclusions last under a "## Marginal" heading, each with the same fields plus one
  short line saying why it is marginal.

If there are no new matches, still create the issue, with the body:

  No new matching jobs today.

Silence is indistinguishable from a failed run, so the issue is created every day
either way.

End the body, in both cases, with one of:
  Coverage: all sources verified.
  Coverage gap: <comma-separated source names>
Name the sources only — no sentence explaining each failure. One exception, worth a
single line: if an unreachable source held a posting that looked like a real match and
you could not date-verify it, say which posting and where, so she can check it by hand.

End the body with the attribution footer: a blank line, a --- rule, then
_Generated by [Claude Code](https://claude.ai/code)_

If the issue POST fails, retry once. If it fails again, do not stop silently — write
the full report to reports/YYYY-MM-DD.md in the repo and commit it, so the content is
not lost, and say clearly in the commit message that issue creation failed.
